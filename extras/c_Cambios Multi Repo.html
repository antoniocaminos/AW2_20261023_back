De dónde venimos

Semana 1
Backend puro

API REST con Express. Probada con Postman. Sin frontend.

Semana 2
Monorepo

Front dentro del back, en public/. Express servía HTML, CSS y JS.

Semana 3 (hoy)
Multi repo

Front afuera, en su propio repo. Cada uno levanta por su lado. Aparece el file://.

La idea central de hoy

Hasta ahora teníamos un monolito simpático: todo vivía adentro del mismo proyecto. El backend servía el frontend con una línea de código:

app.use(express.static('public')); // El backend le decía al navegador: "acá tenés los HTML, CSS y JS"

Hoy rompemos ese matrimonio. El backend ya no sabe nada del frontend. El frontend vive en otra carpeta, en otro puerto, en otro repo. Y para hablarle al backend, va a pedirle datos por HTTP, con una URL explícita.

🍽️ Analogía: hasta ahora tenías un food truck que cocinaba y vendía en el mismo lugar. Ahora tenés la cocina en un local y el salón en otro. Los dos siguen siendo el mismo restaurante, pero se organizan distinto. Al mozo (el fetch) le tenés que dar la dirección completa de la cocina, no alcanza con decirle "ahí al lado".

Cambios en el backend

El backend cambió muy poco. Solo sacamos lo que servía al front.

❌ Antes
import path from 'path';
import { fileURLToPath } from 'url';
const __dirname = ...;

app.use(express.static(
  path.join(__dirname, 'public')
));

app.get('/', (req, res) =>
  res.redirect('/login.html')
);
✅ Ahora
// (no hace falta path ni url)

// (no servimos public)

app.get('/', (req, res) => {
  res.json({
    ok: true,
    mensaje: 'API Usuarios activa',
    endpoints: [...]
  });
});
Los 3 cambios puntuales
  1. 1 Se borró express.static('public'). Ya no hay front que servir.
  2. 2 Se borró el redirect / → login.html. Ese HTML ya no existe acá.
  3. 3 La ruta / ahora devuelve JSON con la lista de endpoints. Sirve para verificar que el backend está vivo.
El resto del backend NO cambió. Rutas, controllers, middlewares y datos quedan igual. Solo dejamos de servir al front.

Cambios en el frontend

El front cambió una sola cosa real: la URL del backend. Antes era condicional, ahora es fija.

❌ Antes
const BACKEND_PORT = 3000;

export const API_URL =
  location.port === '3000'
    ? '/usuarios'            // mismo origen
    : `http://localhost:3000/usuarios`;

Funcionaba en mono repo, pero era frágil.

✅ Ahora
// El front SIEMPRE vive en otro puerto.
// El back SIEMPRE está en el 3000.
export const API_URL =
  'http://localhost:3000/usuarios';

Una línea. Sin condicionales. Sin sorpresas.

Y aparece el error más famoso de todos: si abrís el login.html con doble clic, el navegador usa file:// y bloquea los type="module". Lo vemos en la sección siguiente.

CORS pasa de opcional a obligatorio

En la Semana 2, CORS era "por las dudas". Hoy es obligatorio porque front y back siempre están en puertos distintos.

Semana 2

Front y back en el mismo puerto (3000).

  • Sin CORS también funcionaba.
  • El navegador veía mismo origen.
  • CORS era "por si alguien abría con Live Server".
Semana 3

Front en 5500, back en 3000.

  • Sin CORS, no funciona.
  • El navegador bloquea por origen distinto.
  • El error aparece en la consola, no en el backend.
Cómo lo dejamos configurado
// index.js del backend import cors from 'cors'; const app = express(); app.use(cors()); // 👈 abierto a cualquier origen
🏢 Analogía: el backend es un edificio con portero. CORS es el cartel en la puerta que dice "acepto mensajeros de cualquier edificio". Si no está el cartel, el mensajero de otro edificio no entra, aunque tenga la dirección correcta.
Ojo: CORS es una regla del navegador, no del backend. Postman y curl no la aplican. Si algo funciona en Postman pero no en el navegador, sospechá de CORS.

El error de file://

Este error apareció en clase y es de los más comunes. Vale la pena entenderlo porque te lo vas a encontrar toda la carrera.

// Lo que el navegador te dice Access to script at 'file:///C:/.../js/login.js' from origin 'null' has been blocked by CORS policy: Cross origin requests are only supported for protocol schemes: chrome, chrome-extension, data, http, https.
¿Qué está pasando?

Abriste el login.html con doble clic. El navegador entonces lo carga con el protocolo file://, que significa "este archivo vive en el disco duro". El navegador lo trata como origen null.

Y resulta que los <script type="module"> no se pueden cargar desde file://. Solo se pueden cargar desde http:// o https://. Es una regla del navegador, no de tu código.

Mal
file:///C:/Users/.../login.html

Origen null. El navegador bloquea los módulos.

Bien
http://localhost:5500/login.html

Origen http://localhost:5500. Los módulos cargan sin problema.

🔌 Analogía: es como querer enchufar un cargador europeo en un tomacorriente argentino. El cargador está bien, el tomacorriente está bien, pero el formato no coincide. Los módulos necesitan http:// o https://, no file://.

Mono repo vs Multi repo

📦 Monorepo

Todo el código en un solo repositorio.

✅ Cuándo usarlo

  • Proyecto nuevo o MVP.
  • Equipo chico (1-5 personas).
  • Mismo equipo hace front y back.
  • Un solo deploy, un solo server.

❌ Cuándo NO

  • Equipos grandes con permisos distintos.
  • Deploys independientes (Vercel + Render).
  • Stack muy distinto entre front y back.
🧩 Multi repo

Un repositorio por proyecto.

✅ Cuándo usarlo

  • Equipos separados front / back.
  • Deploys independientes.
  • Mobile + web + back como repos distintos.
  • Cada repo con su propio CI/CD.

❌ Cuándo NO

  • Proyecto chico con un solo dev.
  • MVP rápido que necesita velocidad.
  • Cuando no hay equipo para mantener la separación.
🍔 Analogía: un food truck que cocina y vende en el mismo lugar es un monorepo. Una franquicia con la cocina central en un lado y varias sucursales en otros es multi repo. Los dos venden lo mismo, pero se organizan distinto.

Casos de uso reales

Empresas que todos conocemos y qué eligen:

Empresa / Producto Estrategia Por qué
Google Monorepo Un repo gigante con todo el código. Miles de ingenieros, pero herramientas internas para manejarlo.
Meta (Facebook) Monorepo Un repo enorme con Facebook, Instagram, WhatsApp, backend, mobile y web.
Netflix Multi repo Decenas de microservicios, cada uno con su repo y su equipo.
Spotify Multi repo Equipos autónomos con deploys independientes.
Vercel / Railway Multi repo Cada servicio se deploya por separado. Front a Vercel, back a Railway.
🏢 Analogía: pensá en McDonald's. La casa central define el menú, las recetas y los precios (backend). Cada sucursal tiene su local, su equipo y su horario (frontend). Cambian cosas localmente sin frenar al resto. Eso es multi repo.

Para llevar

  1. 1 Backend y frontend pueden vivir separados. No siempre van juntos. Depende del tamaño del proyecto.
  2. 2 CORS pasa a ser obligatorio cuando front y back están en puertos distintos. No es opcional.
  3. 3 Nunca abras HTML con type="module" desde file://. Siempre servidor HTTP.
  4. 4 api.js se simplifica: una URL fija al backend. Menos condicionales, menos errores.
  5. 5 Monorepo para empezar, multi repo para escalar. No hay una respuesta correcta universal.
  6. 6 El contrato de la API es lo único que comparten. URLs, métodos, body y status codes. Todo lo demás es libre.
