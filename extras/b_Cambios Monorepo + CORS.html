Mono repo vs Multi repo

Monorepo = un solo repositorio con todo el código. Multi repo = varios repos, uno por proyecto.

📦 Monorepo estamos acá

Front y back en el mismo repo.

proyecto/
├── controllers/
├── public/
│   ├── login.html
│   └── js/
├── routes/
└── index.js

✅ Ventajas

  • Un solo git clone y ya está todo.
  • Cambios front+back en un mismo commit.
  • Fácil de arrancar, ideal para aprender.

❌ Desventajas

  • Un repo gigante a medida que crece.
  • Difícil asignar permisos por equipo.
  • Si cae el repo, cae todo.
🧩 Multi repo semana que viene

Un repo para el front, otro para el back.

backend/
├── controllers/
├── routes/
└── index.js

frontend/
├── login.html
├── dashboard.html
└── js/

✅ Ventajas

  • Equipos independientes (front / back).
  • Deploys separados (Vercel para front, Render para back).
  • Cada repo tiene su propio README y CI.

❌ Desventajas

  • Dos git clone, dos npm install.
  • Sincronizar versiones de la API cuesta más.
🍔 Ejemplo real: un food truck que cocina y vende en el mismo lugar es un monorepo. Un restaurante con cocina en un local y salón en otro es multi repo. Los dos funcionan, pero se organizan distinto.
Regla práctica: empezás con monorepo (más simple). Cuando el equipo crece o el front se vuelve una app pesada (React, mobile), pasás a multi repo.

¿Qué es CORS y por qué lo necesitamos?

CORS = Cross-Origin Resource Sharing. Es una regla del navegador (no del servidor) que dice: "una página web solo puede pedir datos a su mismo origen, salvo que el otro origen lo autorice explícitamente".

¿Qué es "origen"? Es la combinación de:

  • Protocolo → http:// vs https://
  • Dominio → localhost vs midominio.com
  • Puerto → :3000 vs :5500 ⚠️

Si cualquiera de los tres cambia, es otro origen y el navegador bloquea la petición… a menos que el servidor responda con la cabecera Access-Control-Allow-Origin.

El problema típico

Front en localhost:5500
Back en localhost:3000
→ Son orígenes distintos.
→ El navegador bloquea sin CORS.

🏢 Analogía: imaginá que tu navegador es un edificio de oficinas. Cada página web que abrís es una oficina. Por defecto, una oficina no puede mandar mensajeros a otras oficinas, salvo que la otra oficina haya puesto un cartel de "acepto mensajeros de cualquier lado". Ese cartel es app.use(cors()).
Cómo lo resolvimos nosotros
// index.js import cors from 'cors'; const app = express(); app.use(cors()); // 👈 autoriza a cualquier origen app.use(express.json());
Ojo: cors() sin argumentos deja pasar a cualquiera. Está bien para desarrollo. En producción se configura con la lista de orígenes permitidos.

sessionStorage vs localStorage

El navegador nos da dos cajones donde guardar datos del lado del cliente. No son cookies: viven en el navegador y se acceden con JavaScript puro.

sessionStorage localStorage
¿Cuánto dura? Se borra al cerrar la pestaña Queda hasta que se borre manualmente
¿Comparte entre pestañas? No, cada pestaña tiene el suyo Sí, todas las pestañas ven lo mismo
Capacidad ~5 MB ~5-10 MB
Persiste al apagar la PC No Sí
¿Para qué lo usamos? Guardar la sesión del login "Recordarme" / preferencias
📝 Analogía: sessionStorage es el pizarrón de la clase: lo escribís hoy, mañana se borra. localStorage es tu cuaderno: queda guardado hasta que vos decidas borrarlo.
Uso concreto en nuestro proyecto
// Al loguear OK (login.js) sessionStorage.setItem('user', JSON.stringify({ email, nombre }) );
// Al entrar al dashboard const user = JSON.parse( sessionStorage.getItem('user') ); if (!user) location.href = './login.html';
Importante: sessionStorage y localStorage NO son seguros para guardar tokens. Cualquiera con DevTools los puede leer. Por eso la semana que viene pasamos a JWT en cookies httpOnly.

Flujo completo del login

Qué pasa paso a paso desde que el usuario aprieta "Ingresar":

👤 Usuario completa form 📤 login.js hace fetch 🧩 api.js arma URL 🛡️ CORS autoriza 🛣️ Router matchea 🧠 Controller valida 🗄️ Lee JSON 📥 Respuesta 💾 sessionStorage 📊 Redirect a dashboard
Todo esto ocurre en menos de 100 ms y en la consola del backend ves cada paso con el logger.middleware.js.

El caso 3000 vs 5500

En clase nos pasó esto y vale la pena contarlo porque es súper común cuando se arranca con front+back.

Con Live Server (:5500)

El front se sirve desde el 5500, el back está en el 3000. Son orígenes distintos.

// login.js antes await fetch('/usuarios/login'); // 👆 se resuelve a http://localhost:5500/usuarios/login // ❌ Live Server no tiene esa ruta → 405
Solución con api.js

Centralizamos la URL. Si detectamos que no estamos en el puerto del backend, apuntamos explícito al 3000.

const API_URL = location.port === '3000' ? '/usuarios' : 'http://localhost:3000/usuarios';
📞 Analogía: es como marcar un número interno en una oficina. Si estás adentro (mismo puerto), marcás "123" y listo. Si llamás desde afuera, tenés que marcar "011-4555-1234" completo.

api.js: el puente entre front y back

Todo el front hace sus llamadas a través de este archivo. Cambia en un solo lugar y se actualiza en todos lados. 

// public/js/api.js
export const api = {
  login:      (email, pass) => request('POST',   `${API_URL}/login`, { email, pass }),
  listar:     ()            => request('GET',    `${API_URL}`),
  crear:      (u)           => request('POST',   `${API_URL}`, u),
  actualizar: (id, datos)   => request('PUT',    `${API_URL}/${id}`, datos),
  eliminar:   (id)          => request('DELETE', `${API_URL}/${id}`)
};

Beneficios concretos:

  • Si cambia la URL del backend, se cambia en un solo archivo.
  • Los fetch con try/catch quedan encapsulados.
  • Es el primer paso hacia un cliente HTTP propio, como Axios.
  • Se importa igual desde login.js y dashboard.js.

Para llevar

  1. 1 Express sirve el front con una sola línea: express.static('public').
  2. 2 CORS es la regla del navegador que permite (o bloquea) pedir datos entre orígenes distintos.
  3. 3 sessionStorage = pizarrón de la clase (se borra al cerrar). localStorage = cuaderno (queda).
  4. 4 Monorepo es más simple para empezar. Cuando el equipo crece, se separa.
  5. 5 api.js centraliza todas las llamadas al backend. Cambia en un lugar, funciona en todos.
  6. 6 Nunca guardes tokens en storage. Se leen desde DevTools. La semana que viene, JWT + cookies.
